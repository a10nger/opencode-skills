# Delegate

Цель — не жечь облачные токены на механике. `local-worker` — локальный исполнитель, стоит ноль, но ошибается чаще. Точную модель и бэкенд не называть по памяти и не брать из этого файла: перечитать `C:\Users\zhega\.config\opencode\agents\local-worker.md` и `C:\Users\zhega\.config\opencode\opencode.json`. Любое название модели, приведённое здесь или в промпте, не является выводом команды.

## Что делегировать

- Прочитать файл и вернуть конкретные строки/факт.
- Найти файлы по шаблону, найти вхождения строки.
- Поиск информации: веб, документация библиотек, API; вернуть источник и цитату.
- Одна правка в одном файле с точно известным содержимым.
- Запустить известную команду (сборка, тест, `git status`) и вернуть результат.
- Собрать вывод: версии, размеры, список процессов.

## Что делать самому

- Планировать и решать, что делать; формулировать задачу воркеру.
- Проверять ответ воркера: важный факт перечитать своим вызовом инструмента перед тем, как говорить пользователю.
- Больше 2 файлов или правки взаимозависимы.
- Требования размытые — сначала надо решить **что** делать.
- Безопасность: секреты, права, удаление данных, реестр, сеть.
- Дизайн/архитектура, ревью, объяснение trade-offs.
- Воркер уже провалил этот шаг дважды.

## Формат задачи

Нумерованный план, ≤15 строк, без воды:

```
1. Прочитай C:\path\file.json и верни строки 10-25 дословно.
2. В C:\path\x.ts замени 'old' на 'new' (единственное вхождение).
3. Запусти: git -C C:\work\repo status --short
4. Верни отчёт по формату ниже.
```

Обязательно:
- **абсолютные пути** (у воркера другой cwd);
- точная команда целиком, а не «проверь сборку»;
- явное «не делай ничего кроме перечисленного»;
- не более одного действия на пункт;
- для важного факта — требование перепроверить его вторым вызовом инструмента и указать источник `path:line`.

Нельзя:
- «посмотри и исправь если надо» — воркер начнёт импровизировать;
- передавать задачу с условием «если X, то сделай Y, иначе Z» — не удержит;
- просить «покажи файл целиком» — контекст ограничен, ответ обрежется.

## Важные факты

Значение из промпта, скила, конфига агента или прошлых сообщений считается недоверенным. Воркер обязан прочитать источник инструментом, повторить проверку вторым вызовом (grep/read) и приложить `path:line`. Если вывод инструмента противоречит ожидаемому — побеждает вывод инструмента.

## Формат ответа воркера

```
STATUS: DONE | FAILED
FILES: <изменённые пути или none>
COMMANDS: <что запускал, одна строка>
RESULT: <ключевое значение + источник path:line>
ERROR: <блокирующая ошибка или none>
```

Это тот же формат, что в `agents/local-worker.md`. Если отчёт не по формату или важное значение без источника — проверять факт самостоятельно, а не верить дословно.

## Батчинг

Независимые шаги отправлять **одним** промптом (пункты 1–5), а не пятью вызовами: каждый вызов — холодный старт и повтор контекста.

## Признаки провала (забирать себе)

- Воркер утверждает «готово», но файл не изменился.
- Правит не тот файл / создаёт дубликат вместо правки.
- Игнорирует абсолютный путь и работает в своей папке.
- Дважды возвращает одну и ту же ошибку.
- Выдумывает содержимое файла вместо чтения.
- Берёт правдоподобное значение из контекста вместо вывода инструмента.

## Цена

Каждый вызов воркера — время и риск. Мелкая задача на 3 строки иногда быстрее делается напрямую. Делегировать, когда шаг действительно механический, а не «на всякий случай».
